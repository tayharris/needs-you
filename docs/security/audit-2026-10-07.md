## Fixed

### 1. High: invite codes in the access log

`Handler.log_message` (`hub/needs_you_hub.py:1560`) wrote `BaseHTTPRequestHandler`'s request
line, which for `GET /join/<code>` and `/join/<code>/install.sh` contains the invite code. On a
server hub that goes to journald; the Mac app pipes its local hub's stderr into the unified log
with `privacy: .public` (`mac/Sources/NeedsYou/LocalHubController.swift:243,249`), so every
invite opened against the app's hub was readable with `log show`. Hard rule 3 forbids this.

Exploit: anyone who can read the logs (another admin account on the Mac, log shipping, a log
excerpt pasted into a bug report) redeems the invite before it's used up or expires and gets a
token with the invite's role, possibly `owner`.

Fix: `redact_log()` (`:1543`) replaces `/join/<anything>` with `/join/<code>`, and anything
shaped like an invite code or token with `<redacted>`, before writing. It also escapes control
characters, so a client-controlled request line can't inject terminal escapes into a journal
viewer (Python 3.9 doesn't). Tests: `HubAbuse.test_access_log_never_shows_invite_codes`,
`test_redact_log`.

### 2. Medium: unbounded read on a negative Content-Length

`Handler._body` (`:1584`) passed `int(Content-Length)` to `rfile.read()`. A negative length
passed the `> limit` check and `read(-1)` reads until the client closes the connection.
`/v1/invites/redeem` reads its body before any auth, so any tailnet peer could stream data
into hub memory until it was killed. Fix: a negative length is a 400. Test:
`test_negative_content_length_is_refused_without_reading`.

### 3. Medium: out-of-range timestamps break listings

`parse_ts` (`:117`) accepted any number of epoch seconds, including `1e13`, `Infinity`
(Python's `json` accepts it) and huge digit strings. A value that fits SQLite but is past year
9999 was stored, and `fmt_ts` then raised on every `GET /v1/items` that included the item.
Any sender token could break every reader's feed with one `expires_at` (a reader token with
`seen_at`), and the record replicated to every peer. Fix: timestamps must be within
1970-01-01..9999-12-31; NaN and infinities are refused. `docs/API.md` documents the range.
Tests: `Timestamps.*`, `test_far_future_expiry_cannot_break_the_feed`,
`test_far_future_seen_at_is_refused`.

### 4. Medium: drive-by connect to a rogue hub

`AppDelegate.handleOpen` (`mac/Sources/NeedsYou/AppDelegate.swift:150`) redeemed any
`needsyou://connect?hub=…&code=…` link immediately. Any web page (or a link in chat) can open
that URL. A page could connect the app to a hub it runs: that hub's cards then appear in the
panel (phishing "approve this" cards, `urgent` cards that break through snooze) and it learns
the Mac's host name.

Fix: links opened from outside the app now show an alert naming the hub (`Connect` /
`Cancel`) before anything is sent; the text comes from `ConnectLink.confirmation`
(`mac/Sources/NeedsYouCore/Connect.swift:105`). Pasting a link into Settings is already a
deliberate act and is unchanged. Test: `SecurityAuditTests.testConnectConfirmationNamesTheHub`
(the alert itself is UI and isn't unit-tested).

### 5. Medium: a new hub re-keying known hubs

`HubListMerge.merge` stored the redeemed token for every URL in the response's `hub_urls`,
including hubs already configured. A rogue hub (see 4, or any hub the user joins) could list the
user's real hubs and overwrite their working tokens with its own, cutting the panel off from
them until the user reconnected.

Fix (`Connect.swift:469`): when the link's hub is new, returned URLs that are already
configured are skipped (reported in `skipped`). Reconnecting through a known hub still
refreshes every hub it names. Test: `testNewHubCannotRekeyKnownHubs`.

### 6. Medium: bidi and invisible-character spoofing

The hub refused ASCII control characters only. Bidi embedding/override/isolate controls
(U+202A–U+202E, U+2066–U+2069) make a title or label display reversed or reordered text, and
zero-width or format characters in a URL make it look like a different one. Agents copy text
from tickets and PRs, so a prompt-injected agent could post them.

Fix: the hub (`:203`, `:205`) refuses C1 controls and bidi overrides in every text field, and
whitespace or invisible format characters anywhere in a link URL (the Mac's `LinkPolicy`
already refused these in URLs, since `CharacterSet.controlCharacters` includes format
characters). Ordinary RTL text, LRM/RLM and ZWJ/ZWNJ (emoji, Persian) stay valid.
`LimitedMarkdown.render` also strips bidi overrides from card bodies, covering older or
replicated items. Tests: `SpoofingAndSchemes.*` (Python: 23 rejected and 6 accepted cases,
including mixed-case, whitespace, tab/newline-split, percent-encoded, `data:`, `file:` and
lookalike schemes); `testLinkPolicyRejectsSchemeTricks`, `testMarkdownNeverKeepsADisallowedLink`
(autolinks, reference links, nested brackets, entity-encoded and angle-bracket destinations,
images), `testMarkdownStripsBidiControls` (Swift).

### 7. Low: no socket timeout

`ThreadingHTTPServer` starts a thread per connection and the handler set no timeout, so a client
that connected and sent nothing (or stopped reading) held a thread for good. Fix:
`Handler.timeout = 60` (`:1558`). SSE streams are unaffected: they write a heartbeat every 15 s.

### 8. Low: shell syntax into the sourceable env file

The invite installer's env writer (`hub/join-install.sh`) wrote the hub's `token` and
`hub_urls`, and the user's `--hub`, into `~/.config/needs-you/env` unchecked. That file is
documented as sourceable (`. ~/.config/needs-you/env`), so a malicious or compromised hub (or a
prompt-injected agent choosing `--hub`) could plant `$(…)` that runs when the user sources it.
`scripts/setup-sender.sh` already validated both. Fix: tokens must match
`[A-Za-z0-9._~+/=-]+` and URLs `https?://[A-Za-z0-9.:/_~%@[]-]+`, checked before anything is
downloaded or written (`:267`, and the `--hub` check after option parsing). Tests:
`InstallerEnvFile.*`.

### 9. Low: template placeholders substituted more than once

`install_script` replaced each `__NY_X__` placeholder in turn, so a value containing another
placeholder name was substituted again inside its quotes, breaking the shell quoting. Only
replicated invite names (from a peer) could carry one. Fix: one `re.sub` pass (`:2254`). Test:
`test_install_script_substitutes_in_one_pass`.

### 10. Low: replicated items bypassed link validation

`normalise_item_record` stored a peer's `links` as given. A peer (or an older hub version) could
store a `javascript:` or `file:` link; the Mac app's `LinkPolicy` still refused to open it.
Fix: replicated records keep only links that pass `link_allowed()` (`:239`, `:1294`), the same
rule as `POST /v1/items`. Test: `test_replicated_items_lose_disallowed_links`.

### 11. Low: terminal escapes from hub responses

`needs-you health`, `doctor` and error paths printed `hub_id`, token names, versions and error
messages from the hub verbatim. Fix: `clean()` (`cli/needs-you:117`) escapes C0/C1 controls
and bidi overrides. Test: `CliOutput.test_clean_neutralises_terminal_escapes`.

### 12. Low: nested JSON

`json.loads` raises `RecursionError` on deeply nested input; it fell through to the generic
handler as a 500. Now a 400. Test: `test_deeply_nested_json_is_a_400`.

### 13. Info: checkout credentials

Every `actions/checkout` now sets `persist-credentials: false`, so the job's `GITHUB_TOKEN`
(which has `contents: write` in the release job) isn't left in `.git/config` for build scripts.
The release step uses `GH_TOKEN` explicitly and doesn't need it.

## Open at audit time (current status in each heading)

### 14. Medium: editor and Orca URI handlers (fixed on `tay/security-links`)

The allow-list admits all of `vscode://` and `cursor://`. Besides `vscode://file/<path>`, those
schemes reach every installed extension's URI handler (`vscode://<publisher.extension>/…`) and
`vscode://vscode-remote/ssh-remote+<host>/…` opens a remote connection. Extension URI handlers
have a history of serious bugs, and VS Code asks for confirmation for some, not all. `orca://`
handlers weren't reviewed (Orca is closed source here). Any sender token, or an agent talked into
it, can post such a link; the user has to click it.

Recommendation: restrict `vscode`/`cursor` to the `file` and `vscode-remote` authorities in
both the hub and `LinkPolicy.swift` (hard rule 7: change both), and list what Orca's handlers
do before keeping `orca://` wide open. This narrows what senders can post, so it needs a call.

**Fixed** (the owner said to go ahead) in commits `61a3982` and `bfd4af6`:

- `vscode://` and `cursor://` open only four shapes, one regex byte-identical in the hub
  (`EDITOR_LINK_PATTERN`) and `LinkPolicy.editorLinkPattern`:
  `file/<abs path>[:line[:col]]`; `vscode-remote/ssh-remote+<host>[/<abs path>]`;
  `vscode-remote/tunnel+<name>[/<abs path>]`; `anthropic.claude-code/open?session=<id>` (path
  `/open`, exactly one `session` parameter of 8–64 letters, digits or `-`; the Claude Code
  hook's VS Code link). The authority is matched exactly in lowercase; the scheme
  case-insensitively. Remote host names must start with a letter or digit and contain no
  `%` (Remote-SSH has had `-oProxyCommand` option-injection bugs), and an all-hex name
  starting `7b` is refused (Remote-SSH reads it as a hex-encoded JSON host spec that could
  carry such an option). `tunnel+` is kept: a Remote Tunnel can only reach tunnels on the
  user's own GitHub/Microsoft account. `wsl+` is refused (Windows only; the app is macOS) and
  `dev-container+` and `attached-container+` are refused (they build or attach to a container
  from a config the link names, which runs code). Paths refuse escapes that decode into
  structure or into another escape (`%2F %3F %23 %2E %25 %5C`), escaped controls and `.`/`..`
  segments; queries and fragments are refused on file and remote links.
- **`orca://` is dropped.** Nothing in the repo needs it: Orca (1.4.220) has no terminal or
  worktree links, its only link is `orca://skills/share/<id>`, which imports a skill (a card
  should never be able to ask for that), and the Orca jump is the app's own
  `needsyou://orca/terminal`.
- Every link, of every scheme and the app actions included, must first match one raw grammar
  on both sides (`LINK_RAW_PATTERN` / `LinkPolicy.rawLinkPattern`): plain ASCII,
  `<scheme>://`, no userinfo `@`, no backslash, quotes, `[]<>^`` ` ``{|}`, whitespace or
  controls, `%` only as `%XX`, at most one `#`; `https` needs a host. The scheme is read from
  the raw string, never from `urlsplit` or `URL`, so the hub and the app can't parse one
  string two ways. `tests/fixtures/link_cases.json` (131 cases) runs on the hub
  (`test_link_mirror.py`) and on `LinkPolicy` (`LinkCasesTests.swift`); the only allowed
  difference is an app action the hub accepts by prefix and the app's parser refuses.
- Replicated items and steps go through the same `link_allowed()` (#10), so a peer can't
  bring back a refused link (`test_replicated_items_lose_refused_editor_links`).
- Every link the repo's senders write still passes (the hook's file, Remote-SSH and Claude
  links, `cursor://file{cwd}` templates, the demo fixture, the GitHub poller's https links;
  `test_every_automatic_link_passes_the_hub`). The hook posts its card again without links when
  the hub refuses a custom `NEEDS_YOU_AGENT_LINK`. Tests: `tests/test_editor_links.py`,
  `LinkPolicyTests.testEditorLink*`.

### 15. Low: link label vs destination

As with any Markdown, `[GitHub PR](https://…)` can point anywhere on `https`. Bidi tricks are now
gone (6), but plain mislabeling isn't. Done on `tay/mac-ui-pass` (commit "mac: show each link's
real host next to its label"), not on this branch: every allowed link button shows its https host
(or its scheme) after the label, never shortened, via `LinkRowPolicy.destination(_:)`, tested by
`CardLayoutTests.testLinkDestinationShowsTheRealHost`. SECURITY.md still tells users to check
where a link goes.

### 16. Low: DNS rebinding (fixed on `tay/security-links`)

The hub doesn't check `Host`. A web page in the user's browser can rebind its name to
`127.0.0.1` and read the unauthenticated endpoints: `/v1/health` (hub id, version, counts) and
`/dl/*` (public files). Everything else needs a token or an invite code, which a page can't get,
and there are no CORS headers (tested), so this leaks little. Recommendation: accept only `Host`
values for loopback, the bind addresses, the MagicDNS name and `public_url`.

**Fixed** in commit `27bb6f6`. Every endpoint checks `Host` first. Accepted: any IP literal (a
rebinding page's `Host` is always its own DNS name, so an IP can't be one; this covers
`127.0.0.1`, the tailnet `100.x` and peers that use IPs), `localhost`, non-IP bind names,
the `public_url` host and, for a `*.ts.net` name, its short form, the machine's host name
(full, short, `<short>.local`), `<public_url label or short host name>.<any tailnet>.ts.net`,
and `allowed_hosts`. Any other name is **421** `misdirected`; a malformed `Host` is 400; a
request without `Host` (HTTP/1.0, never a browser) is served. The Mac app's embedded hub is
started with `--public-url http://<MagicDNS name>:8765` and binds `127.0.0.1` plus the tailnet
IP, and the app, local senders and peers call it by those, so nothing legitimate changes.
Escape hatch: `allowed_hosts` in the config, `--allowed-host NAME`, or
`NEEDS_YOU_HUB_ALLOWED_HOSTS` (comma-separated; the app's hub inherits it from the app's
environment, `launchctl setenv`); `*` turns the check off. The CLI and the Mac client treat
421 like a transport error and try the next hub; `needs-you doctor` explains it. Tests:
`tests/test_host_check.py`.

### 17. Low: installer and release integrity (mostly fixed; the signing key is the owner's step)

`curl … | bash`, the CLI the installer downloads and `needs-you self-update` all travel as plain
`http` inside the tailnet: integrity rests on Tailscale's encryption, plus a syntax check of the
downloaded CLI. Release assets have `SHA256SUMS`, but it is produced by the same job that builds
them and isn't signed. Recommendations: put the sha256 of each `/dl` file on the join page and
check it in the installer; add build provenance (`actions/attest-build-provenance`) or a signing
key for releases. A signing key is an owner decision.

**Update on `tay/auto-update` (automatic updates).** Self-update makes this matter more, so:

- *Mac app.* Only from `api.github.com` and GitHub's release-asset hosts over https, redirects
  included (anything else is refused, and the token is sent to `api.github.com` only); the repo
  is fixed in code; the manifest and the zip are assets of the same release; the zip must match
  both `release-manifest.json` and `SHA256SUMS`; the release run must be `success` on the
  manifest's commit when Actions is readable; the unpacked app must have the same bundle id, the
  promised and a newer version, a valid seal, the same signing team as the running app (when it
  has one), and no symlink leaving the bundle; it is unpacked into a fresh directory only the user
  can write. A local test feed (`updateFeedURL`) must be a `file://` path, shows a warning in
  Settings, and never installs automatically.
- *Senders.* Automatic updates are **off by default** (`NEEDS_YOU_AUTO_UPDATE=1` or the
  installer's `--auto-update` opts in). `needs-you update` asks only the hub the machine was
  invited by (the first `NEEDS_YOU_URLS` entry, or `NEEDS_YOU_UPDATE_HUB`), never a failover hub
  or a URL a hub supplies; only over https, loopback or the tailnet; checks each file against the
  hub's `/dl/manifest.json`; and, when `gh` can read the repo, against the GitHub release of that
  version (refusing on any mismatch, and with `NEEDS_YOU_UPDATE_REQUIRE_RELEASE_MATCH=1` when the
  check can't run). Every verification error refuses (a `gh` that is installed but fails, a
  missing manifest field, an unreadable checksum file); automatic updates require the release match
  unless `NEEDS_YOU_UPDATE_REQUIRE_RELEASE_MATCH=0`. The hub URL is parsed once, a `*.ts.net`
  name resolved once, and the connection pinned to that address (Host header, no redirects), so
  DNS rebinding and URL-form tricks can't move it off the checked address. It never downgrades without `--allow-downgrade` and keeps backups for
  `needs-you update --rollback`.

**What's still missing: authenticity.** A checksum fetched from the same place as the file proves
integrity, not who made it. Anyone who can publish a release on the repo (or steal the token
that does) can ship an update the Mac will install, and a compromised invite hub can still serve
senders that have no `gh`. The real fix is a signature: a Developer ID signature (with a pinned
team in the updater), and/or an Ed25519 key over `release-manifest.json`. The Mac side is built:
`UpdateAuthenticity.pinnedManifestKey` in `mac/Sources/NeedsYouCore/Updater.swift` (nil today);
once set, `release-manifest.json.sig` (base64 Ed25519 signature over the manifest bytes,
verified with CryptoKit, no dependency) is required. To turn it on, the owner must: create the
key pair offline (for example `openssl genpkey -algorithm ed25519`), store the private key only
as an Actions secret (`RELEASE_MANIFEST_SIGNING_KEY`) and offline, add a release step that writes
`release-manifest.json.sig`, and pin the base64 raw public key in the app. No private key was
generated or committed. The CLI can't verify Ed25519 with the Python stdlib, so until there's a
stdlib-verifiable scheme (or a release-signed hash list it can check another way), senders rely
on the invite-hub, transport and GitHub cross-check rules above.

**Update on `tay/security-links`** (commits `738f534`, `a6b1417`):

- *(a) Installer.* The sender join page ends with **Files and checksums** (each `/dl` file's
  sha256, the same values as `/dl/manifest.json`), and `install.sh` embeds that list as served.
  The installer checks the CLI, the hook files, the skill and the Orca snippet (and
  `install-hooks.sh` on `--uninstall`) against it and refuses a file that doesn't match or isn't
  listed, before installing anything from it (`tests/test_install_integrity.py`). Integrity, not
  authenticity: it catches corrupt or partial downloads and binds the files to the page the
  user saw.
- *(b) Provenance.* The release job attests every asset, `release-manifest.json` and
  `SHA256SUMS` included, with `actions/attest-build-provenance` pinned to the v4.2.2 commit
  `4d10147…`; `id-token: write` and `attestations: write` are on the release job only. Verify
  with `gh attestation verify <file> --repo tayharris/needs-you`. GitHub attests public
  repositories only on this plan, so the step is skipped while the repo is private.
- *(c) `needs-you update`.* With `gh`, the release cross-check also downloads the release's
  `release-manifest.json`, requires it to list the server tarball it compared against, and runs
  `gh attestation verify` on that downloaded file (argument array, 120 s timeout) pinned with
  `--repo tayharris/needs-you`, `--signer-workflow …/.github/workflows/release.yml`,
  `--source-ref refs/tags/vX.Y.Z`, the SLSA predicate type and `--deny-self-hosted-runners`,
  with `--format json`. It parses the result and requires the subject sha256 to equal the
  file's computed sha256, plus the repository, ref, signer workflow and `github-hosted` runner
  in the certificate. Each installed file is bound to the attested manifest through checksums
  (hub file == tarball copy, tarball sha256 == manifest entry == `SHA256SUMS`). A non-zero
  exit, empty or invalid JSON, a timeout or a mismatch refuses the update, like the release
  match (`ReleaseCrossCheck` tests: wrong repo, workflow, ref, predicate, self-hosted runner,
  digest, bad JSON, exit 1). The one exception is a private repository (asked with `gh api`
  after a failed verify), which can't have attestations and gets a note instead. Release builds
  on a self-hosted runner (`RELEASE_MAC_RUNNER`) are refused by design; see
  [release-signing.md](release-signing.md).
- *(d) Signing.* A release step signs `release-manifest.json` with Ed25519 (OpenSSL 3, verified
  before upload, `release-manifest.json.sig`) when the `RELEASE_MANIFEST_SIGNING_KEY` secret
  exists, and prints an "Unsigned release" notice when it doesn't. No key was generated or
  committed.

**Remaining owner step:** create the Ed25519 key offline, store it as the
`RELEASE_MANIFEST_SIGNING_KEY` secret, and pin its public key in
`UpdateAuthenticity.pinnedManifestKey`, exactly as in
[release-signing.md](release-signing.md). Until then the Mac updater doesn't require a
signature. Making the repository public turns on build provenance for releases and its check in
`needs-you update`.

### 18. Low: Python 3.9.6 on macOS

The hub and CLI run on macOS's `/usr/bin/python3` (3.9.6, CPython end of life since October
2025). Relevant stdlib CVEs fixed after 3.9.6, and why they don't bite here:

- CVE-2020-10735 (quadratic `int()` on long digit strings): a 64 KiB JSON number costs some
  CPU per request. Minor; nothing to fix without a dependency-free guard.
- CVE-2023-24329 (`urlsplit` and leading blanks): the hub strips and refuses control characters
  and spaces before calling `urlsplit`.
- CVE-2021-3737 (`http.client` loop on endless `100 Continue`): client side only, and the CLI and
  peers only talk to configured hubs.
- `tarfile`, `zipfile`, `email`, `xml`, `pickle`: not used, so their CVEs don't apply.
- `http.server` CVE-2021-28861 (open redirect): `SimpleHTTPRequestHandler` only, which isn't
  used.

Ubuntu 22.04 (3.10) and 24.04 (3.12) get distro security fixes. Nothing to do now; revisit if
Apple ships a newer Python or the project bundles one (an ADR).

### 19. Low: hook arguments starting with `-`

The Claude Code hook passes the title (from the project directory's name), the body (from the
notification message) and the project as separate argv entries, so there's no shell injection.
But argparse reads a value like `-x` as an option, the CLI exits 2 and the card is silently lost.
Fix: pass `--title=…`, `--body=…`, `--project=…`. Done on `tay/claude-sender-setup` (commit
"claude hook: pass title, body and project as --opt=value", with a test), not on this branch.

### 20. Accepted by design

- Any web page can open `needsyou://orca/terminal?handle=…`. The app validates the handle and
  environment (tested against flags, separators, non-ASCII digits, extra parameters,
  user/port/fragment and path tricks) and runs only `orca terminal switch` from a fixed path with
  an argv array. Worst case: Orca shows a different terminal tab.
- A sender token can resolve any open key; a peer secret can write any record, token hashes
  included. Both are documented in SECURITY.md.
- `/v1/health` is unauthenticated (documented).
- The app starts its local hub with the user's environment, without `python3 -I`. Only the user
  can set that environment.

## Checked and fine

- **Tokens:** `ny_` + 256 random bits; only sha256 is stored, looked up by hash (comparison
  timing reveals nothing useful); printed only at mint. Peer secret compared with
  `hmac.compare_digest`, at least 16 chars when peers are set. The Mac's `tokens.json` is written
  atomically at 0600 in a 0700 directory; the owner token file is 0600.
- **Invites:** `nyi_` + 192 random bits, sha256 only, at most 100 uses and 90 days, revocable,
  failed redeems rate-limited per IP. `/v1/invites` never returns codes after creation.
- **Roles:** every endpoint checked for no token, unknown token, sender, reader and owner
  (`test_role_matrix`); replication endpoints accept only the peer secret.
- **SQL:** every query is parameterized; table names are constants. Tested with quote
  metacharacters in keys and ids.
- **`/dl` and `/join`:** `/dl` is a fixed name-to-file map (traversal attempts tested). The served
  `install.sh` gets every value through `_sh_quote`, and the code it embeds is only ever one that
  matched a stored hash.
- **Network:** bind to `0.0.0.0`, `::`, `[::]`, empty or `*` refused unless overridden (tested);
  no CORS headers, so a browser can't read responses or send the `Authorization` header cross-site.
- **Sender files:** env file 0600 (setup-sender and installer), outbox entries 0600 in a 0700
  directory, no token in outbox entries; `setup-sender.sh` passes the token to curl through a
  mode-600 header file, never argv.
- **Hook:** reads stdin JSON with `json.loads` in Python, builds the CLI call as an argv list,
  `shlex.quote`s the displayed command, accepts only `^term_[0-9a-f-]{8,64}$` handles and safe
  environment names in the Terminal link, sanitizes the session id used for file names.
- **Mac app:** `Process` is used with fixed executable paths and argument arrays (Orca CLI, the
  local hub); `LimitedMarkdown` parses inline-only, drops images and any link `LinkPolicy`
  rejects, and every click goes through `OpenURLAction` → `AppModel.open`, which checks again.
- **Site:** no third-party scripts, fonts or fetches; a strict CSP in `site/_headers`.
- **CI:** actions pinned by full SHA; both pins checked against the `v7.0.1` tags, the current
  releases. Workflows default to `contents: read`; untrusted values reach shell steps through
  `env`, not `${{ }}` interpolation.
